# ChatGPT и Home Assistant через HA‑MCP

[English](README.md) | **Русский**

Полная инструкция по установке, безопасной настройке, проверке, устранению ошибок и откату

**Версия документа:** 1.0  
**Дата проверки:** 18 сентября 2026 года  
**Статус:** опубликованная обезличенная инструкция
**Проект HA‑MCP:** неофициальный community‑проект, не входящий в состав Home Assistant или OpenAI

> Эта инструкция не содержит рабочих webhook URL, токенов, паролей, адресов частной сети, идентификаторов устройств и других секретов. Все примеры используют заполнители. Никогда не публикуйте полный путь после `/api/webhook/`.

## 1. Что получится после настройки

ChatGPT сможет обращаться к Home Assistant через Model Context Protocol (MCP). В зависимости от разрешённых инструментов он сможет:

- находить устройства и сущности по понятным названиям;
- читать текущие состояния, погоду, энергопотребление и историю;
- анализировать автоматизации, сценарии, трассировки и системное состояние;
- управлять устройствами и вызывать сервисы;
- создавать и изменять автоматизации, сценарии, помощники и панели;
- работать с резервными копиями, приложениями и реестрами;
- при установке дополнительных компонентов читать и изменять разрешённые YAML‑файлы;
- при установке отдельного движка Puppet получать снимки интерфейса Home Assistant.

Конкретный набор возможностей определяется одновременно четырьмя уровнями:

1. тарифом и возможностями ChatGPT;
2. версией и способом установки HA‑MCP;
3. включёнными инструментами HA‑MCP;
4. режимом безопасности: только чтение, подтверждение изменений или разрешённая запись.

## 2. Важное ограничение ChatGPT

По документации OpenAI на дату этой инструкции:

- полная работа с пользовательскими MCP‑приложениями, включая действия записи, предоставляется в ChatGPT Business и Enterprise/Edu;
- Pro может подключать MCP в developer mode с ограничениями на чтение и получение данных;
- настройка пользовательского приложения выполняется в веб‑версии ChatGPT;
- приложение ChatGPT подключается к удалённому MCP‑серверу, а не напрямую к локальному адресу домашней сети.

Перед установкой откройте в ChatGPT **Settings → Apps → Advanced Settings** и убедитесь, что доступен developer mode и создание пользовательского приложения. Возможности тарифов меняются, поэтому перед публикацией или повторной установкой сверяйтесь с актуальной [инструкцией OpenAI](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt).

## 3. Какую архитектуру выбрать

### Вариант A — HACS‑компонент со встроенным сервером

Это текущий рекомендуемый upstream‑вариант для новой установки.

Подходит, если:

- Home Assistant Core не ниже 2026.8 для установки через HACS;
- нужен один компонент без отдельного приложения HA‑MCP и Webhook Proxy;
- нужен встроенный webhook, панель настройки и OAuth `ha_auth`;
- планируется использовать актуальные возможности проекта.

Компонент устанавливается из репозитория `homeassistant-ai/ha-mcp-integration`. Он запускает HA‑MCP внутри Home Assistant, создаёт собственный webhook и может требовать вход через учётную запись Home Assistant.

### Вариант B — приложение HA‑MCP и Webhook Proxy

Это фактически проверенный у нас вариант:

- Home Assistant Core 2026.9.2;
- Home Assistant MCP Server 8.5.0;
- Webhook Proxy 3.0.3;
- OAuth‑режим `ha_auth`;
- начальная работа только на чтение;
- успешная авторизация ChatGPT;
- успешное чтение состояний;
- после отдельной настройки — подтверждённое управление воротами.

Он подходит для Home Assistant OS/Supervised и остаётся полезным, если приложение уже установлено и работает. Для новой установки сначала рассмотрите вариант A.

### Вариант C — секретный webhook без OAuth

Это штатный стабильный запасной режим HA‑MCP. Полный URL является паролем. Любой, кто получит его, сможет вызвать доступные MCP‑инструменты.

Используйте этот вариант, если OAuth конкретного клиента не проходит и нужно быстро получить ограниченное подключение только на чтение. После диагностики лучше вернуться к `ha_auth`.

### Что нельзя совмещать

- Не запускайте встроенный сервер и отдельное приложение HA‑MCP как два параллельных сервера для одного подключения.
- Не добавляйте в ChatGPT два подключения к одному Home Assistant.
- Не запускайте Stable и Dev‑варианты Webhook Proxy одновременно: они конфликтуют за OAuth‑маршруты.
- Не оставляйте старое приложение ChatGPT после смены webhook URL или режима авторизации.

## 4. Модель безопасности

### `ha_auth`

Рекомендуемый режим для доступа из интернета. Пользователь входит через Home Assistant. Встроенный сервер допускает только администратора, потому что сам HA‑MCP работает с административными полномочиями.

Преимущества:

- webhook URL сам по себе недостаточен для доступа;
- сессию можно отозвать в профиле Home Assistant;
- не нужно копировать статический Client Secret;
- ChatGPT поддерживает автоматическое обнаружение OAuth.

### `none` — URL как секрет

OAuth‑проверки нет. Полный webhook URL является bearer‑секретом.

Правила:

- не показывать URL на скриншотах;
- не вставлять его в обращения, публичные конфигурации и журналы;
- не хранить его в Git;
- при возможной утечке немедленно сгенерировать новый URL;
- сначала включать только чтение.

### `legacy`

Устаревающий режим со статическими Client ID и Client Secret. Используйте только для клиента, который не умеет `ha_auth`. Секрет предоставляет доступ, поэтому обращаться с ним нужно так же строго, как с webhook URL.

### Режим только чтения

Начальная установка должна выполняться с:

```yaml
read_only_mode: true
redact_secrets: true
verify_ssl: true
enable_auto_backup: true
enable_snapshot_delete: false
```

`read_only_mode` должен блокировать вызовы изменения на стороне сервера. Одного обещания в системном сообщении ChatGPT недостаточно.

## 5. Предварительная проверка

Перед изменениями зафиксируйте:

- версию Home Assistant Core и тип установки;
- наличие HACS;
- работающий внешний HTTPS‑адрес Home Assistant;
- состояние критичных устройств и автоматизаций;
- состояние камер, если они используются;
- свободное место для резервной копии;
- текущие приложения HA‑MCP, прокси и пользовательские компоненты;
- наличие Stable или Dev‑веток;
- доступность developer mode в ChatGPT.

Проверьте внешний адрес с телефона через мобильный интернет. Он должен открывать Home Assistant по HTTPS. Локальный адрес вида `192.168.x.x` для облачного ChatGPT недоступен.

### Обязательная резервная копия

Перед установкой или расширением прав создайте полную резервную копию Home Assistant и проверьте:

- резервная копия появилась в списке;
- она завершена без ошибки;
- известны её дата, размер и версия Home Assistant;
- понятно, как выполнить точечный откат;
- полное восстановление не будет применяться поверх более поздних полезных изменений без отдельного решения.

## 6. Рекомендуемая новая установка через HACS

### 6.1. Установка компонента

1. Откройте HACS.
2. Выберите **Integrations → ⋮ → Custom repositories**.
3. Добавьте:

   ```text
   https://github.com/homeassistant-ai/ha-mcp-integration
   ```

4. Выберите категорию **Integration**.
5. Установите **HA‑MCP Custom Component**.
6. Перезапустите Home Assistant Core.
7. После запуска откройте **Settings → Devices & Services → Add Integration**.
8. Найдите **HA‑MCP Custom Component**.
9. Выберите **HA‑MCP Server**.

Не выбирайте **File & YAML Tools**, если файловые и YAML‑инструменты пока не нужны.

### 6.2. Начальная конфигурация

Рекомендуемые настройки:

- Release channel: `stable`;
- Automatic server updates: выключить на время пилота или контролировать обновления вручную;
- Network access: `127.0.0.1`, если прямой LAN‑порт не нужен;
- Remote access via webhook: включить для ChatGPT;
- Authentication mode: `ha_auth`;
- External URL: официальный внешний HTTPS‑адрес Home Assistant;
- Read Only Mode: включить;
- Redact secrets: включить;
- автоматические резервные копии изменений: включить;
- удаление полных snapshots: выключить;
- beta/dev‑инструменты: выключить до отдельной проверки.

Скопируйте URL только с административного экрана **Configure**. Не помещайте его в эту инструкцию, GitHub или общие заметки.

### 6.3. Настройка ChatGPT

1. Откройте веб‑версию ChatGPT.
2. Включите developer mode.
3. Откройте **Settings → Apps → Create**.
4. Укажите понятное уникальное имя, например `Мой дом HA — только чтение`.
5. Вставьте актуальный MCP webhook URL.
6. Выберите OAuth.
7. Не вводите статические Client ID и Client Secret для `ha_auth`.
8. Нажмите **Scan Tools**.
9. Пройдите вход Home Assistant под административной учётной записью.
10. Проверьте список инструментов до создания приложения.
11. Создайте приложение и включите его в новом чате.

Если ChatGPT уже видел этот URL или прежний набор инструментов, используйте новое имя приложения. Кэш может сохраняться даже после удаления и повторного добавления под прежним именем.

## 7. Установка через HA‑MCP Server + Webhook Proxy

Этот раздел воспроизводит схему, успешно проверенную у нас.

### 7.1. Установка

1. Добавьте репозиторий приложений:

   ```text
   https://github.com/homeassistant-ai/ha-mcp
   ```

2. Установите **Home Assistant MCP Server**.
3. Установите **Webhook Proxy for HA MCP**.
4. Убедитесь, что Dev‑вариант Webhook Proxy остановлен или отсутствует.
5. Настройте MCP Server в режиме только чтения.
6. Запустите MCP Server и проверьте его журнал.
7. Запустите Webhook Proxy.
8. Выполните перезапуск Home Assistant, если его требует карточка Repairs первоначальной установки.

### 7.2. Настройки MCP Server для пилота

```yaml
backup_hint: strong
read_only_mode: true
redact_secrets: true
verify_ssl: true
enable_tool_search: false
enable_security_policy_tool: false
enable_snapshot_delete: false
enable_auto_backup: true
```

Названия параметров могут измениться. Сверьте их с установленной версией.

### 7.3. Настройки Webhook Proxy

- `mcp_port`: порт установленного MCP Server;
- `enable_oauth`: включено;
- `oauth_mode`: `ha_auth`;
- OAuth Client ID: пусто;
- OAuth Client Secret: пусто;
- `remote_url`: пусто при корректном автоматическом определении Nabu Casa либо точный внешний HTTPS‑адрес;
- `debug_logging`: выключено, включать временно только для диагностики.

После сохранения перезапустите приложение прокси. Полный перезапуск Core нужен при первичной регистрации интеграции, при запросе Repairs и для некоторых legacy/старых переходов режима. В актуальном `ha_auth` сам переход режима обычно требует только перезапуска приложения. Следуйте документации именно установленной версии.

### 7.4. Подключение ChatGPT

Создайте приложение с актуальным webhook URL, выберите OAuth и оставьте Client ID/Secret пустыми. После входа Home Assistant выполните **Scan Tools**.

## 8. Запасной режим без OAuth

Если ChatGPT отклоняет OAuth до страницы входа:

1. Не объявляйте это общей несовместимостью ChatGPT и OAuth.
2. Сначала сохраните журналы без секретов и проверьте причины из раздела диагностики.
3. Для временного пилота выключите OAuth в HA‑MCP.
4. Перезапустите требуемый компонент согласно документации своей версии.
5. При необходимости сгенерируйте новый webhook URL.
6. Убедитесь, что старый URL больше не отвечает.
7. В ChatGPT удалите старое приложение.
8. Создайте приложение с другим именем.
9. Выберите **No authentication**.
10. Выполните Scan Tools.
11. Оставьте сервер в режиме только чтения.

Прямая проверка webhook должна выполняться настоящим MCP `POST initialize`, а затем `tools/list`. Открытие URL в браузере — недостаточная проверка. Ответ `405 Method Not Allowed` на обычный `GET` может быть нормальным.

## 9. Приёмочные проверки

### 9.1. Проверки сервера

- HA‑MCP запущен без циклических рестартов;
- webhook или OAuth discovery доступны по внешнему HTTPS;
- неавторизованный запрос в режиме `ha_auth` отклоняется;
- `initialize` завершается успешно;
- `tools/list` возвращает непустой список;
- в режиме только чтения попытка изменения блокируется до выполнения;
- секреты маскируются;
- Home Assistant остаётся в состоянии Running;
- критичные устройства, автоматизации и камеры работают как до установки.

### 9.2. Проверки через ChatGPT

В новом чате выберите созданное приложение и последовательно попросите:

1. `Покажи версию Home Assistant и ничего не изменяй.`
2. `Найди погоду у дома и покажи текущее состояние.`
3. `Проверь состояние [безопасной сущности], ничего не переключай.`
4. `Покажи, какие инструменты доступны только для чтения.`

Затем выполните отрицательную проверку без реального воздействия:

`Проверь, доступна ли команда изменения, но не выполняй её.`

В режиме только чтения фактическая запись должна быть запрещена сервером.

### 9.3. Что считать успешным результатом

- ChatGPT видит актуальный список инструментов;
- чтение возвращает реальные текущие значения;
- `unavailable` не подменяется нулём;
- изменения не проходят без разрешения;
- старый URL после ротации не работает;
- анонимный запрос не получает данные в защищённом режиме;
- после проверки нет новых ошибок Home Assistant.

## 10. Как безопасно разрешать управление

Не отключайте Read Only Mode сразу для всех инструментов. Расширяйте возможности ступенями:

1. чтение;
2. отдельное безопасное устройство;
3. отдельный сценарий;
4. создание автоматизаций и помощников;
5. панели и реестры;
6. файловые/YAML‑инструменты;
7. системное обслуживание.

Для каждого изменяющего инструмента желательно:

- явное поле подтверждения;
- серверная проверка подтверждения;
- автоматическая резервная копия перед изменением;
- проверка результата после записи;
- отказ от автоматического повтора при тайм‑ауте;
- журналирование без секретов;
- отдельный rollback.

### Особый случай: ворота, замки и сигнализация

Для физически значимых действий безопаснее создать ограниченный инструмент, который:

- умеет только открыть или закрыть конкретный объект;
- не принимает произвольный `entity_id`;
- требует `confirm: true`;
- читает состояние перед командой;
- ограничивает частоту повторов;
- не повторяет импульс после тайм‑аута;
- возвращает `result unknown`, если команда отправлена, но подтверждение состояния не получено.

У нас общий HA‑MCP первоначально оставался только для чтения, а четыре команды ворот были добавлены через отдельный ограниченный фасад. Это снизило риск произвольных сервисных вызовов.

## 11. Дополнительные возможности

### File & YAML Tools

Нужны только для прямой работы с разрешёнными файлами и YAML. Устанавливаются отдельной записью интеграции **HA‑MCP File & YAML Tools**.

Риски:

- ошибка может перевести Home Assistant в recovery mode;
- восстановление тогда потребует SSH или File Editor;
- некоторые операции перезаписывают файл целиком;
- удаление файла не имеет корзины;
- `command_line` может запускать команды;
- config check не обнаруживает все логические ошибки интеграций.

Включайте после резервной копии и сначала проверяйте чтение. Для автоматизаций, сценариев, помощников и панелей предпочитайте специализированные инструменты HA‑MCP, а не прямую правку YAML.

### Снимки панелей через Puppet

Puppet — отдельный движок Chromium, а не часть HA‑MCP. Для него нужен long‑lived access token Home Assistant.

Рекомендуется:

- создать отдельного пользователя только для Puppet;
- не использовать личный основной токен;
- не публиковать порт Puppet в LAN или интернет без необходимости;
- включить автозапуск и watchdog;
- проверить реальный PNG на мобильном размере;
- помнить, что текущие версии Puppet могут менять тему профиля своей учётной записи.

У нас были установлены File & YAML Tools и Puppet 2.6.0. Снимок панели 390×844 был получен и визуально проверен. Для Puppet использовалась отдельная локальная учётная запись, а порт не публиковался в LAN.

## 12. Реальные проблемы, встретившиеся у нас

### 12.1. ChatGPT читал состояния, но не управлял воротами

**Симптом:** ChatGPT сообщал, что включён Read Only Mode или что команды управления отсутствуют.

**Причины:**

- сервер действительно работал только на чтение;
- специальные команды ворот ещё не были добавлены;
- после добавления ChatGPT продолжал использовать старый каталог инструментов.

**Исправление:**

- общий сервер оставили только для чтения;
- добавили четыре строго ограниченные команды ворот;
- потребовали отдельное подтверждение;
- проверили, что произвольный сервисный вызов запрещён;
- обновили подключение ChatGPT.

### 12.2. Новый инструмент был на сервере, но ChatGPT его не видел

**Симптом:** `tools/list` на сервере содержит новые команды, а ChatGPT показывает старые 40 инструментов.

**Причина:** кэш каталога инструментов ChatGPT.

**Исправление:** удалить приложение и создать его с новым именем. Добавление под прежним именем может сохранить старый каталог.

### 12.3. Команда ворот завершилась тайм‑аутом

**Симптом:** ChatGPT сообщил, что команда отправлена, но результат неизвестен.

**Причина:** импульс мог быть отправлен, а подтверждение конечного состояния не пришло вовремя.

**Правильное поведение:** не отправлять команду повторно автоматически. Сначала повторно прочитать состояние, затем пользователь решает, нужен ли второй импульс.

### 12.4. Ограниченный фасад не мог прочитать Home Assistant

**Симптом:** connection refused при чтении состояния ворот.

**Причина:** был выбран неправильный локальный API‑порт Home Assistant.

**Исправление:** заменить endpoint на фактически доступный локальный HTTP‑адрес, проверить его отдельным чтением и только после этого разрешать команды. Ошибка чтения должна явно означать: физическая команда не отправлена.

### 12.5. Открытые ворота считались уже полностью открытыми

**Симптом:** пользователь просил открыть приоткрытые ворота, а команда подавлялась из‑за состояния `open`.

**Причина:** бинарный датчик не различал частичное и полное открытие.

**Исправление:** по явному подтверждённому запросу разрешить один импульс даже при состоянии `open`; не повторять автоматически.

### 12.6. ChatGPT не находил стиральную машину и сушилку

**Симптом:** поиск не находил устройство, хотя энергосенсоры существовали.

**Причина:** в реестре осталось старое имя «Розетка сервер».

**Исправление:** присвоить устройству и сущностям однозначные пользовательские имена, не меняя `entity_id` без необходимости. После исправления поиск нашёл датчики мощности, тока, напряжения и энергии.

**Вывод:** качество естественного поиска зависит от имён устройств, областей и сущностей. Перед обвинением MCP проверьте реестр Home Assistant.

### 12.7. Недоступная розетка отображалась как нулевое потребление

**Симптом:** устройство не на связи, но ответ воспринимался как 0 Вт.

**Правило:** `unavailable` и `unknown` нельзя подменять нулём. В инструкции для ассистента следует явно потребовать показывать недоступность отдельно.

### 12.8. Другой чат говорил, что панель изменить нельзя

**Симптом:** инструмент панели фактически присутствовал, но конкретный чат отвечал, что доступа нет.

**Причины:** приложение не было выбрано в чате, старый каталог инструментов, другой диалог или модель не вызвала инструмент.

**Исправление:** открыть новый чат, явно выбрать приложение, попросить сначала перечислить/прочитать панель, затем выполнить изменение с подтверждением.

### 12.9. File/YAML и screenshot‑инструменты отображались, но не работали

**Причина:** сервер зарегистрировал инструменты, однако дополнительные компоненты File & YAML Tools и Puppet ещё не были установлены.

**Исправление:** установить зависимости отдельно, после резервной копии и с отдельной проверкой. Наличие названия инструмента не доказывает готовность его backend.

### 12.10. OAuth считали несовместимым с ChatGPT

**Симптом:** ChatGPT отклонял соединение до страницы входа.

**Ошибочный вывод:** «ChatGPT не совместим с Beta OAuth Webhook Proxy».

**Фактический вывод:** наша схема `ha_auth` успешно прошла вход и работала. Отказ до авторизации обычно связан с discovery, регистрацией клиента, внешним URL, reverse proxy, кэшем или конфликтом версий. Secret URL является допустимым обходом, но не доказывает несовместимость OAuth.

## 14. Теоретические ошибки и способы исправления

### Несовпадение External URL

Домен и схема, по которым ChatGPT открывает Home Assistant, должны соответствовать External URL Home Assistant. Reverse proxy обязан корректно передавать `Host`, `X-Forwarded-Host` и `X-Forwarded-Proto`. Иначе `issuer` и OAuth‑маршруты могут сформироваться как относительные или с другим доменом.

### Клиент требует DCR, а сервер предлагает CIMD

Нативный Home Assistant MCP использует Client ID Metadata Document и не предоставляет классический RFC 7591 registration endpoint. Клиент, который жёстко требует DCR, может отказать до входа. HA‑MCP Webhook Proxy `ha_auth` добавляет совместимый слой регистрации для поддерживаемых клиентов.

### TLS и сертификаты

Просроченный сертификат, неполная цепочка, редирект с HTTPS на HTTP или сертификат другого домена блокируют облачный клиент. Проверяйте с внешнего устройства, а не только из домашней сети.

### WAF, геоблокировка и защита от ботов

Cloudflare/WAF может пропустить браузер владельца, но заблокировать серверы ChatGPT. Временно включите безопасное журналирование, установите, приходит ли запрос, и добавьте точечное правило. Не отключайте всю защиту без необходимости.

### Слишком медленный reverse proxy

OAuth discovery, регистрация и token exchange имеют тайм‑ауты. Уберите лишние редиректы, проверьте DNS, cold start и задержку прокси.

### Старый transport MCP

Некоторые клиенты и серверы расходятся по версии streamable HTTP/SSE. Обновите обе стороны и проверьте `initialize`. Не заменяйте протокол обычным REST GET.

### Prompt injection через данные Home Assistant

Названия, уведомления, календари, веб‑страницы и другие внешние данные могут содержать вредные инструкции для модели. Ограничивайте write‑tools, проверяйте подтверждение на сервере и не разрешайте произвольный код без необходимости.

### Слишком широкая административная учётная запись

Встроенный HA‑MCP использует административный токен. Поэтому ограничение должно обеспечиваться инструментами и policy‑движком HA‑MCP, а не ожиданием, что обычный HA‑пользователь автоматически уменьшит права backend.

### Скрытые сущности не являются полноценной защитой записи

Фильтр видимости по умолчанию сокращает результаты чтения, но сам по себе может не блокировать адресный write‑вызов. Для управления нужны Tool Security Policies и enforce‑режим.

### Несовместимые автоматические обновления

Сервер HA‑MCP и HACS‑компонент версионируются отдельно. Новый сервер может потребовать более новый компонент. Устанавливайте обновления контролируемо, читайте Repair и не обходите удержание версии без резервной копии.

## 15. Эксплуатация и обновления

Перед обновлением:

1. сохранить версии сервера, компонента и прокси;
2. создать резервную копию;
3. экспортировать список включённых инструментов и policies без секретов;
4. проверить release notes;
5. обновить один слой;
6. проверить `initialize` и `tools/list`;
7. проверить чтение через ChatGPT;
8. проверить отрицательный write‑тест;
9. только после этого обновлять следующий слой.

После изменения списка инструментов создайте новое приложение ChatGPT с новым именем, если старое продолжает показывать кэш.

## 16. Отключение и откат

### Временно отключить связь с ChatGPT

1. Отключить или удалить пользовательское приложение в ChatGPT.
2. Отозвать его сессию/refresh token в профиле Home Assistant.
3. Остановить Webhook Proxy или выключить Remote access via webhook.
4. Проверить, что внешний endpoint больше не принимает запросы.

### Откат add-on‑схемы

1. Остановить Webhook Proxy.
2. Остановить HA‑MCP Server.
3. Выключить их автозапуск и watchdog.
4. Не удалять резервную копию.
5. Проверить Home Assistant, камеры и автоматизации.
6. Удаление proxy‑интеграции выполнять отдельно, только если установка больше не нужна.

Не восстанавливайте полный snapshot только ради удаления HA‑MCP: он может затереть более поздние изменения Home Assistant.

### Откат встроенного сервера

1. Отключить Remote access via webhook либо удалить HA‑MCP Server entry.
2. Убедиться, что выданный внутренний токен отозван.
3. При необходимости удалить HACS‑компонент и перезапустить Core.
4. Проверить исходные функции Home Assistant.

## 18. Публичная публикация в GitHub

Перед публикацией выполните автоматическую и ручную проверку.

Запрещено публиковать:

- полный webhook URL;
- сегмент после `/api/webhook/`;
- MCP secret path;
- OAuth Client Secret;
- access и refresh tokens;
- long‑lived access token Puppet;
- внутренние IP‑адреса и hostname без необходимости;
- реальные entity ID ворот, замков и сигнализации;
- журналы, содержащие заголовки Authorization;
- резервные копии Home Assistant;
- скриншоты с домашними данными.

Рекомендуемая структура будущего репозитория:

```text
README.md
docs/
  installation.md
  security.md
  troubleshooting.md
  rollback.md
examples/
  read-only-options.example.yaml
  tool-policy.example.json
.gitignore
LICENSE
SECURITY.md
```

Этот файл можно использовать как исходник для `README.md`, но перед публикацией желательно:

- ещё раз проверить версии и тарифы;
- разделить большой текст на короткие документы;
- добавить английскую версию;
- добавить предупреждение об unofficial‑статусе;
- проверить все внешние ссылки;
- выполнить secret scan;
- не включать реальные production‑конфигурации.
